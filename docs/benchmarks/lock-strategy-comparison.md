# 락 전략 비교 — v0~v4 실측

## 측정 조건

- 환경: PostgreSQL 16 + Redis 7 (로컬, Docker Compose)
- k6: 100 VU, 200 iterations
- 초기 잔액 10,000원, 회당 출금 100원
- 재현: `make test` (전체) / `make test-v2`, `make test-v3`, `make test-v4` (개별) — [test.js](../../test.js)

## 2026-07-26 재측정 — v1 / v2 / v4 3파전

기존 표는 전략별로 측정 시점이 달라 직접 비교가 어려웠다. 세 전략을 같은 세션에서 다시 쟀다.

**측정 방식이 달라진 점**
- `make test`(전체 순차)의 요약은 모든 시나리오를 합산해 버전별 비교에 못 쓴다 → `k6 run test.js -e VERSION=<v>` 개별 실행
- 전체 실행을 워밍업으로 먼저 돌린 뒤 측정 (첫 실행이 JIT 컴파일 비용을 떠안는 교란 제거)
- 지연은 **성공 건만** (`http_req_duration{expected_response:true}`), 실패는 응답 코드별 Counter로 분리

원본 출력: [raw/2026-07-26-k6-v1-v2-v4.txt](raw/2026-07-26-k6-v1-v2-v4.txt)

| 전략 | iterations/s | 성공 avg | 성공 p90 | 성공 p95 | 전체 p95 | 200 / 400 / 409 | 최종 잔액 | 검산 | 정합성 |
|------|:-----------:|:-------:|:-------:|:-------:|:--------:|:---------------:|:--------:|------|:-----:|
| v1 비관적 락 | **261/s** | 570ms | 656ms | **680ms** | 657ms | 100 / 100 / 0 | 0원 | 10,000 − 100×100 | ✅ |
| v2 낙관적 락 | 246/s | 169ms | 370ms | **392ms** | 410ms | 82 / 0 / 118 | 1,800원 | 10,000 − 82×100 | ✅ |
| v4 Redis 분산락 | 142/s | 501ms | 924ms | **974ms** | 979ms | 100 / 100 / 0 | 0원 | 10,000 − 100×100 | ✅ |

**검산 열은 필수다.** 성공 건수와 최종 잔액은 서로를 검증한다 —
`성공 건수 × 100원`이 차감액과 어긋나면 둘 중 하나가 잘못된 값이다.

### 실패 건 지연 (역산)

`실패 avg = (전체건수 × 전체avg − 성공건수 × 성공avg) / 실패건수`

| 전략 | 성공 avg | 실패 avg | 실패의 성격 |
|------|:-------:|:-------:|------------|
| v1 비관적 락 | 570ms | ~110ms | 락 획득 후 잔액 부족 → 즉시 400 |
| v2 낙관적 락 | 169ms | ~364ms | 재시도 3회 + 백오프 소진 후 409 |
| v4 Redis 분산락 | 501ms | ~673ms | v1과 동일한 400인데 ~6배 (Redis 왕복 비용) |

### 06-28 표와 달라진 점

| 항목 | 2026-06-28 | 2026-07-26 | 비고 |
|------|-----------|-----------|------|
| v1 TPS / 성공 p95 | ~210/s / 845ms | 261/s / 680ms | 워밍업 후 측정 + 성공 건 기준 |
| v2 TPS / 성공 p95 | ~234/s / 482ms | 246/s / 392ms | 〃 |
| v4 TPS / 성공 p95 | ~90/s / 1,620ms | 142/s / 974ms | 〃 — 차이가 가장 크다 |
| v4 대비 v1 손실 | -57% TPS / +92% p95 | **-46% TPS / +43% p95** | 결론(분산락이 가장 느림)은 동일 |

**새로 확인한 것**
- v4의 409(락 획득 타임아웃)가 **0건** — 느린 원인은 락 획득 실패가 아니라 임계 구역 길이다.
  v4의 실패 유형은 v1과 동일하게 100건 전부 400(잔액부족).
- v4 실패 건이 v1 실패 건보다 ~6배 비싸다. 같은 일(락 획득 → 잔액 확인 → 거절)을 하는데도 그렇다.
- **v2의 성공 건수는 실행마다 흔들린다** (같은 조건에서 75 / 76 / 82건). 재시도 성공 여부가
  스레드 스케줄링에 달려 있기 때문이다. v1·v4는 매번 정확히 100건으로 결정적이다.
  잔액은 세 경우 모두 성공 건수와 정확히 일치했다.
- 워밍업 없이 v1을 첫 실행으로 돌리면 261/s → 110/s, 성공 p95 680ms → 1,260ms로 나온다.
  측정 순서 하나로 전략 간 순위가 뒤집히므로 워밍업은 선택이 아니다.

### v4 락 동작 실측 (2026-07-26)

409가 0건인 이유를 Redis 쪽에서 확인했다. 원본 로그와 분석 명령은 [raw/README.md](raw/README.md) 참고.

| 항목 | 값 | 의미 |
|------|:--:|------|
| 락 획득 시도 | 598회 | 요청은 200건인데 시도는 3배 |
| 획득 성공 | 201회 | |
| 획득 실패(`pttl` 반환) | **397회** | 남이 잡고 있어 되돌아감 |
| `SUBSCRIBE` | 1회 | 락 이름당 구독을 공유·참조 카운트로 관리 |
| 고유 소유자 field | 100개 | UUID는 1개(인스턴스) + 스레드 ID 100개 |

397번 튕겼지만 전부 `WAIT_SECONDS = 3` 안에 재획득에 성공해 응답에는 타임아웃이 남지 않았다.
응답 코드만 보면 조용하지만 내부적으로는 요청당 평균 3회 재시도가 발생한다.

락 키는 Hash(`ENC = listpack`, `HLEN = 1`)이고 field가 `clientUUID:threadId`, value가 재진입 횟수다.
이 도메인은 `transfer`가 서로 다른 두 키를 잡으므로 재진입이 발생하지 않아 value는 항상 1이다.

## Race condition 재현 (v0)

| 항목 | 정상 | 실제 |
|------|------|------|
| 최종 잔액 | 0원 | **7,800원** |
| 성공 건수 | 100건 | **200건** |

출금 200번이 모두 성공 응답 — 실제 상황이었으면 대형 금융사고. 락 전략 비교의 베이스라인.

## 측정 이력 — 재측정으로 수치가 바뀐 것

두 전략 모두 최초 측정에 버그가 섞여 있었고, 수정 후 재측정한 값이 위 최종 비교표 기준이다.

### v1 비관적 락

| 항목 | 초기 측정 (sleep 버그 포함) | 최종 (재측정) |
|------|------|------|
| TPS | 181/s | **~210/s** |
| p95 | 1,010ms | **845ms** |

v0 대비 실제 TPS 손실은 -13% (초기 측정 기준 -25%보다 작다).

### v2 낙관적 락

마지막 attempt 실패 시 불필요한 400ms sleep이 있었다 (`119건 × 400ms = 47.6초` 낭비). 제거 후 재측정:

| 항목 | sleep 버그 | fix 후 재측정 | 개선 |
|------|-----------|------------|------|
| TPS | ~113.7/s | **~234/s** | +106% |
| p95 | 1,050ms | **482ms** | -54% |

v2 낙관적 락은 v1 비관적 락(~210/s) 대비 **~11% 높은 TPS**.

## 멱등성 (v2.5) 검증

- 정합성: 잔액 1,900원 (음수 없음) ✅
- 멱등성: 50 VU 동일 키 → 100원 1번만 출금, 나머지 49건 모두 200 응답 ✅

## 알려진 이슈 — v1 데드락 취약점 (미수정)

v1 `PessimisticTransactionService.transfer`는 from→to 순서로 DB lock을 획득한다.
A가 `1→2`, B가 `2→1`로 동시 송금하면 교차 락 획득으로 `PostgreSQL deadlock detected`가 발생할 수 있다.
k6가 단방향 송금만 테스트해서 미발견 상태였다. v4는 `Math.min/max` ID 정렬로 해결했다 ([ADR-0004](../adr/0004-redis-distributed-lock-design.md)).
v1에는 동일 패치가 아직 적용되지 않았다.
